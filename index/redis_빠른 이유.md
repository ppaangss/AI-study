# Redis가 빠른 이유

Redis는 명령 하나가 보통 **마이크로초(µs)** 단위로 끝난다. 디스크 기반 DB의 밀리초(ms)와 1000배 차이. 이유는 세 겹이다.

## ① 메모리 기반

RAM 접근 ~100ns vs SSD 접근 ~100µs — 저장 매체 자체가 약 1000배 빠르다. 가장 큰 요인. 나머지 두 이유도 "명령 하나가 원래 순식간에 끝난다"는 이 전제 위에서 성립한다.

## ② 싱글 스레드 + 이벤트 루프

Redis는 명령 처리를 **스레드 하나**로 한다 (Node.js의 이벤트 루프와 같은 구조). 직관과 반대로, 멀티스레드의 숨은 비용이 사라져서 오히려 빠르다:

- **락(lock)이 필요 없음** — 동시에 데이터를 만지는 스레드가 없으니 락 획득/해제, 경합 대기가 전부 사라진다.
- **컨텍스트 스위칭 없음** — 스레드 전환 비용이 없다.

각 명령이 메모리 연산이라 µs 안에 끝나므로, 하나씩 줄 세워 처리해도 초당 10만+ 명령을 소화한다.

> Redis 6.0부터 네트워크 I/O(패킷 읽기/쓰기)는 멀티스레드로 처리 가능해졌지만, **명령 실행 자체는 여전히 싱글 스레드**다.

## ③ I/O 멀티플렉싱

클라이언트 수천 개가 붙어도 `epoll`(리눅스) 같은 OS 기능으로 스레드 하나가 전부 감시한다. "이벤트가 온 소켓만 골라서 처리"하는 방식이라 연결 수만큼 스레드를 만들 필요가 없다.

## 싱글 스레드의 양면성 (중요)

| | 내용 |
|---|---|
| **얻는 것** | 모든 명령이 **원자적**. `INCR`/`DECR`가 실행되는 도중에 다른 명령이 끼어들 수 없다 → 좌석 재고 감소 같은 동시성 제어에 락 고민 없이 쓸 수 있는 이유 |
| **잃는 것** | 명령 하나가 오래 걸리면 **전체가 막힘**. 100만 키를 도는 `KEYS *` 한 방이면 모든 클라이언트가 대기 → "KEYS 금지, big key 주의" 운영 수칙의 근거 |
