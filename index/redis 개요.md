# Redis 개요

Redis = **RE**mote **DI**ctionary **S**erver. 이름 그대로 "네트워크 너머에 있는 딕셔너리(해시맵)". 자바의 `HashMap`을 서버로 만든 것이라고 생각하면 된다.

## 핵심 정체성 3가지

1. **인메모리(In-Memory)** — 모든 데이터를 디스크가 아닌 RAM에 둔다. MySQL은 디스크가 본체고 메모리는 캐시인 반면, Redis는 메모리가 본체다.
2. **키-값(Key-Value) 저장소** — `SELECT ... WHERE` 같은 쿼리가 없다. 키를 알면 O(1)로 가져오고, 모르면 못 가져온다.
3. **자료구조 서버** — 단순 문자열만 저장하는 게 아니라 List, Hash, Set, Sorted Set 같은 자료구조 자체를 값으로 저장한다. 이것이 같은 인메모리 캐시인 Memcached와의 결정적 차이.

## 키와 값의 구조

```
키(key)  →  값(value)
 │           └── 값의 타입은 5가지 중 하나: String / List / Hash / Set / Sorted Set
 └── 키는 항상 그냥 문자열 ("user:1", "stock:seat:42")
```

- String은 5가지 값 타입 중 하나일 뿐이다. String 타입 안에는 문자열·숫자·JSON·바이너리가 다 들어가며, 숫자도 문자열로 저장되고 `INCR` 같은 명령이 올 때만 숫자로 해석된다.
- 컬렉션 타입(List/Hash/Set/ZSet)의 원소는 전부 문자열이다. **중첩 불가** — Hash 안에 Hash, List 안에 List는 안 된다. "1단계 깊이의 자료구조"라는 게 Redis의 특징이자 한계.
- 키 네이밍 관례: `객체:ID:필드`처럼 콜론으로 계층 표현 (`user:1:name`). 문법이 아니라 관례.

## nil

"없음"을 뜻하는 Redis의 응답. 자바의 `null`과 같다. `GET 없는키 → (nil)`. 에러가 아니라 "결과가 없음"이라는 정상 응답이며, 자바 클라이언트로 받으면 `null`로 온다. 캐시 미스 판정(`if (cached == null)`)이 이걸로 이뤄진다.

## "메모리"라는 말의 대가

RAM은 비싸고 작다. 그래서 Redis 설계에 두 가지 질문이 따라다닌다:

1. **메모리가 꽉 차면?** → eviction 정책 ([redis eviction 정책](<redis eviction 정책.md>))
2. **서버가 꺼지면 데이터는?** → RDB/AOF 영속성 (5장에서 공부 예정)

"Redis는 빠르지만, 그 빠름은 '작고 휘발되는 메모리' 위에 서 있다."
