# Redis TTL과 키 만료

주제: "RAM은 작다. 꽉 차기 전에 어떻게 비울 것인가?"의 첫 번째 답 — **TTL(예약 삭제)**. (두 번째 답은 [redis_eviction 정책](<redis_eviction 정책.md>))

## TTL — 키에 수명을 붙이기

TTL(Time To Live) = 키가 살아 있을 시간. 지나면 자동 삭제된다.

```
SET session:abc "{...}" EX 1800    ← 저장하면서 30분 수명 부여
EXPIRE user:1 60                   ← 이미 있는 키에 60초 수명 부여
TTL session:abc                    → 1794  (남은 초)
TTL user:999                       → -2    (키 자체가 없음)
TTL config:app                     → -1    (키는 있는데 수명 없음 = 영구)
PERSIST session:abc                ← 수명 제거, 영구 키로 전환
```

**함정: `SET`으로 값을 덮어쓰면 기존 TTL이 날아간다** (영구 키로 리셋). TTL을 유지하며 값을 바꾸려면 `SET ... KEEPTTL`. 실무 "세션이 안 죽어요" 버그의 단골 원인.

**용도:** 세션(30분 자동 로그아웃), 캐시(5분 뒤 갱신 유도), 인증번호(3분), rate limit 카운터(1분 창구), 분산 락(락 잡은 서버가 죽어도 TTL로 자동 해제).

## 만료된 키는 "언제" 실제로 지워지나

만료 시각에 즉시 지우지 **않는다.** 수많은 키의 만료 시각을 전부 정확히 감시하는 것 자체가 비용이라, 두 전략을 섞는다:

1. **Lazy(게으른) 삭제** — 누가 그 키에 **접근하는 순간** 만료를 확인하고 지운 뒤 nil 반환. 접근 안 하면 방치.
2. **Active(능동) 삭제** — 주기적으로(기본 초당 10회) TTL 달린 키 중 20개를 무작위 샘플링해 만료된 걸 삭제. 지운 비율이 25%를 넘으면(만료 키가 많이 쌓였다는 뜻) 한 번 더 돈다.

결과: **만료 시각 ≠ 실제 삭제 시각.** 다만 만료된 키에 접근하면 반드시 nil을 받으므로(lazy가 보장), 사용자에게는 "만료 즉시 사라진 것처럼" 보인다. 메모리에서 사라지는 것만 늦을 수 있다.

설계 철학: "정확함보다 싸게" — 근사와 샘플링으로 비용을 아낀다 (eviction의 근사 LRU도 같은 철학).

## 설계 감각

**"이 키는 언제 어떻게 사라지는가?"를 키를 만들 때마다 답할 수 있어야 한다.** TTL로 죽나, eviction으로 밀려나나, 영원히 사나 — 답이 없는 키가 메모리 누수의 주범.
