# Redis 유스케이스와 선택 기준

## 대표 유스케이스 5가지

| 용도 | 왜 Redis인가 | 사용하는 기능 |
|---|---|---|
| **캐시** | DB 조회 결과를 메모리에 두고 재사용 → DB 부하↓, 응답속도↑ | String + TTL |
| **세션 저장소** | 서버 여러 대가 세션을 공유해야 할 때 (스케일 아웃) | Hash + TTL |
| **랭킹/리더보드** | 점수순 정렬을 자료구조가 알아서 유지 | Sorted Set |
| **분산 락** | 여러 서버가 "이 자원 내가 잡았다"를 원자적으로 선언 | `SET NX` |
| **큐/메시징** | 작업 대기열, 이벤트 전파 | List, Pub/Sub, Streams |

## 전부 Redis 없이도 해결 가능하다

Redis는 "유일한 해법"이 아니라 "특정 조건에서 가장 싸게 먹히는 해법"이다.

**랭킹 예시** — MySQL로도 된다: `SELECT * FROM scores ORDER BY score DESC LIMIT 10;` + score 인덱스. 갈림길은 **쓰기 빈도**:
- 하루 몇 번 바뀌는 주간 판매 순위 → MySQL로 충분. Redis는 과설계.
- 초당 수천 번 점수가 바뀌고 실시간 "내 순위"까지 보여줘야 하는 게임 리더보드 → MySQL은 쓰기+인덱스 갱신+순위 계산(`COUNT`)이 버거움. Sorted Set은 쓰기 O(log N)에 `ZRANK`가 내장.

Redis가 이기는 지점: "정렬된 상태를 **항상 유지**하면서 읽기/쓰기가 둘 다 잦을 때".

**대안 비교표:**

| 용도 | 대안 | Redis를 고르는 기준 |
|---|---|---|
| 캐시 | 로컬 캐시(Caffeine), Memcached | 서버 여러 대가 **캐시를 공유**해야 할 때. 서버 1대면 로컬 캐시가 더 빠름(네트워크 왕복 없음) |
| 세션 | DB 세션 테이블, JWT(저장 자체를 안 함) | 스케일 아웃 + TTL 자동 만료. JWT로 상태를 없애는 선택지도 흔함 |
| 분산 락 | MySQL `SELECT ... FOR UPDATE`, 네임드 락, ZooKeeper | DB 락은 커넥션을 물고 있어 부하가 크고, ZooKeeper는 견고하지만 운영이 무거움. Redis는 그 중간 |
| 큐/메시징 | Kafka, RabbitMQ, DB 폴링 | 가벼운 작업 큐면 Redis, 유실 불가한 대용량 스트림이면 Kafka. Redis 큐는 메모리라 유실 위험 |

## Redis를 선택하는 공통 논리 3가지

1. **속도** — DB가 감당 못 하는 읽기/쓰기 빈도 (캐시, 리더보드)
2. **공유 상태** — 서버 여러 대가 같은 값을 봐야 함 (세션, 분산 락)
3. **자료구조 내장** — 정렬 유지, TTL 만료를 직접 구현 안 해도 됨

거꾸로: **트래픽이 작거나 서버가 1대면 Redis는 대부분 불필요.**
